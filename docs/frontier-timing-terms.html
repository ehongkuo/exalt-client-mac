Part 2: the ordering proof (backstop)

Accounting (Part 3) clears nearly every hit first. The ordering proof clears what accounting can't: hits during a suspension, heals with no "+N" text, and overcharged debuff hits.

A hit cleared too early is missing from the projection, which can cost a death. A hit cleared too late is counted twice, which can only cause an early escape. So every hit stays pending until the guard can prove an update contains it.

  1. Pair each hit with the next reply. The client replies to every update. The first reply it sends after a hit travels on the same connection, behind the hit, so the server cannot receive the reply before the hit.
  2. Track the latest round trip. Every update carries the round trip of the latest reply the server received. A repeated value means no new reply arrived: ignore it. A new value arrived after the previous update was built, so it belongs to the reply whose build time + value falls between the two build times. That proves the server had that reply, and every earlier message, by build time + value.
  3. Set the hit's proof bound from the first such proof for a reply at or after the first reply after the hit: the hit was received by then at the latest.
  4. Clear the hit on the first update built at least c after the bound. That update is proven to contain it. Until then the hit stays pending, however old it looks.
  5. Project and decide as today. Projected HP = latest server HP − every hit not yet cleared. Escape when a hit takes the projection to 0 or below.

The proof uses only values read from updates (build times, round trip) plus the order of two client sends. Clock offset, upload and download estimates drop out. It holds if:

  • the round-trip field is the latest single measurement, updated as each reply arrives, not an average (about 20% of captured updates repeat the previous value exactly, which supports this; holding replies back in the probe build would confirm it);
  • hit reports and replies share one ordered connection;
  • c is an upper bound on how long before its build an update stops taking messages.

Part 3: accounting with heal text (primary rule)

Server HP is net: a heal in the same update hides part of a hit. Burst heals (pets, allies, beacons) show green "+N" text over the player in the same frame as the update that applies them, and the text is the HP actually gained. Adding it back gives the damage the update applied. The server applies hits in report order, so that damage clears the oldest pending hits.

applied = heal text − HP change − drain allowance (+ regen, left out)
  1. Collect heal text shown over the player since the last update.
  2. Work out the applied damage. Regen is left out, so this is a lower bound. A heal without text also makes it smaller, never larger.
  3. Clear the oldest pending hits by that amount. A hit cleared in part keeps the rest.
  4. Regen residue. If the hit this update partly cleared has 3 HP or less left, clear it. That is regen (about 1 HP per update) hiding the last bit.
  5. Unexplained loss. If more was applied than everything pending, something unreported hit the player. Stop accounting for the rest of the map and leave hits to the ordering proof.
